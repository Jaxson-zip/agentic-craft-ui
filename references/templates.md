# 报告与记录模板

## 交付报告

越短越好，用户先看到结论。小修复写成三行即可。

```markdown
**结果**：<一句话：做成了什么，能不能用；没做成就直接说没做成和原因>

**改动**
- `<文件>`：<改了什么>

**没验证的**
- <具体项和原因；全部验证过就写“无”>

<需要用户决定的事，一句话一个；没有就不写>
```

需要列检查时，附一张短表，只放和这次需求有关的检查：

```markdown
| 检查 | 状态 | 证据 |
| --- | --- | --- |
| <动作 → 可见结果> | passed | <命令或截图路径> |
| 视觉 | 待你验收 | <截图路径> |
```

写的时候注意：

- 核心路径没跑通时，第一行就写没完成，后面的通过项不能盖过它。
- 证据要能复查：命令、文件或截图路径。读源码推断的不算 passed。
- 不复述需求、不罗列所有文件的所有细节、不写过程日志。用户想看细节会问。
- 新界面要写一句视觉选择：强调色（值、领域、第一还是第二选择）、至少一个备选和放弃理由，以及选了[页面布局库](layouts.md)里的哪种布局。

## 当前决定记录

只在**跨多次对话的新产品或大改动**里用，放在项目已有的需求或决策文档里；小功能和修复不写。

```markdown
## 当前决定（YYYY-MM-DD）
- 要做成：<谁> 能 <做什么>，看到 <什么> 才算完成
- 不做：<…>
- 用户已定：<选择>（<日期或原话>）；用户否定过：<…>
- 我的假设：<…>（待确认）
- 下一步：<…>
```

用户的判断用 `selected / rejected / pending`，检查结果用 `passed / failed / blocked / not-run`，两套不要混用。用户没回复不算同意；新反馈只更新它涉及的那一项。
