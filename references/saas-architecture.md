# SaaS 架构与验证

用于多租户、跨业务领域、共享授权或有独立 API/worker 的系统。任务仅改一个现有页面时，沿既有边界调查，不自动开展全产品重建。这里补充 [架构与上下文](architecture-context.md)，不绑定语言、框架、数据库或部署供应商。

## 默认步骤

按顺序推进；后面各节是每一步的细则和常见误区。

1. 提取租户模型、身份、角色与资源权限、关键不变量和运行约束；未知项标为假设。
2. 新系统先按生态调研决定复用，再划分业务模块和数据所有者。
3. 只画需要的视角（运行单元、领域、ER、时序），每张图标注状态。
4. 定义写操作的事务、并发、幂等和异步副作用边界。
5. 打通一条跨过真实边界的纵向路径，用两个租户、多个角色验证隔离与恢复。
6. 分别报告设计、功能、隔离、恢复、UI 和性能证据。

## 先确定系统约束

从需求和现状提取实际的租户模型、主体身份、角色/资源权限、关键业务不变量、数据规模与保留策略、外部集成、运行环境及团队约束。规模未知时标明假设与测量计划，不编造 QPS、SLA 或容量结论。

新 SaaS 在锁定实现前按 [生态调研](discovery.md) 比较整套产品、starter 与模块复用；架构图标出采用的现有组件、需要适配的边界与真正的业务自建部分。学习/隔离实验的手写会话或 worker 不能直接升级为生产底座，功能测试不替代选型依据。

以业务能力划分职责，例如身份与组织、核心业务、计费权益、通知与集成；指出各模块拥有的数据和公开接口。页面菜单与文件目录不能直接当成领域边界。订单、额度或审批一类跨模块规则需要明确最终写入者和一致性要求。

没有既有架构时，比较适合当前约束的方案：模块化单体通常降低初期部署与事务成本；独立 worker 可分离耗时副作用；独立服务适合已经明确的部署、所有权或伸缩边界。不能因为“大型”就自动引入微服务、Kubernetes、Kafka、Redis 或每服务一个数据库。已有架构优先沿用，决策记录说明选择理由与重新评估条件。

## 可审阅的架构产物

沿用项目现有位置；新系统可集中到 `docs/ARCHITECTURE.md`，较长时分文件。根据实际问题提供以下视角，避免画四张同义图：

| 视角 | 应回答的问题 |
| --- | --- |
| 系统边界 / 运行单元图 | 用户、身份提供方、web/API/worker、数据存储与外部系统如何连接？哪些连接跨信任边界？ |
| 领域模块图 | 谁拥有数据与规则？允许依赖什么接口？哪些业务变化会跨模块？ |
| 数据模型 / ER 图 | 租户键、实体关系、唯一约束、版本、事务及生命周期是什么？ |
| 关键时序图 | 一条具体操作如何授权、提交、失败、重试及触发异步副作用？ |

图区分 `proposed`、`implemented` 与 `verified`，允许一张图包含不同状态，但需图例与节点标记。已有系统的关系应附真实文件、路由、迁移或配置依据；只找到 export 时不能画出未经核对的调用关系。拟议设计列出假设，不假装已存在这些文件。

每次改变租户模型、模块接口、事务边界或运行单元时更新受影响图和决策。符号快照只用于定位，不能自动证明架构图最新。轻量目录结构、图纸与实际依赖应互相吻合。

## 身份与租户边界

核对 actor 是谁、tenant 从哪里取得、成员关系是否有效、资源归属是什么。请求里的 tenant ID 可以作为选择，但必须在服务端验证访问资格；不能把任意 header、URL、隐藏按钮或前端过滤当成授权。

资源查询和写入同时约束 tenant 与资源 ID；服务端检查角色、资源权限及合法状态变化。全局唯一的 ID 不免除隔离验证。模型需要时用复合唯一键/外键防止把 A 租户资源关联到 B 租户；软删除、成员撤销和管理员跨租户操作另有明确规则。

隔离要沿实际路径追到列表、搜索、统计、导出、批量操作、缓存键、对象存储、后台任务与外部事件。不要为当前未采用的组件创造整套实现；采用了就检查实际 tenant/actor 如何传播，不能只在首页加过滤。跨租户支持操作应显式授权并留痕。

组织切换时，处理未保存编辑、取消或丢弃旧请求、清理租户相关缓存/选中项；旧租户的慢响应不能覆盖新组织页面。URL/刷新与权限撤销时的恢复需与服务端一致。

对可撤销的写权限，定义撤销与提交的生效边界。中间件通过后仍有异步输入读取、外部等待或排队时，早先的授权可能过期；根据现有一致性方案在实际提交边界核对可变权限，或明确授权快照的业务语义。分别测试撤销后的新请求与正在途中的请求；同一会话仍有效不等于成员关系仍有效。复用身份库不免除这一业务规则，也不意味着必须重写权限引擎。

会话有效性与成员角色是不同的可变状态。要求提交时身份仍有效的业务，也检查输入读取/排队期间注销或会话到期的路径；成员仍存在不能证明会话仍有效。沿实际身份提供方和数据一致性机制处理，不给其他栈强加直接读取本地 session 表的方案。

## 一致性与异步边界

先定义一条写操作的事务内容和并发策略，再决定工具。版本冲突不能通过替换版本号、重发旧字段绕过。幂等键绑定租户、主体/操作范围、请求内容和结果：相同键不同内容应拒绝，保留期与重复返回语义需明确。

业务写入与审计需要一起成功时放在同一事务；不在事务内直接调用邮件、支付或慢网络服务。若要求提交后可靠触发副作用，可采用既有事务 outbox/队列机制：说明事件如何与业务写入原子记录、worker 如何认领/恢复/去重、失败如何重试和人工处理。至少一次投递不等于外部副作用恰好一次；接收方不支持幂等或核对时，明确“已发送但响应丢失”的重复风险。

webhook 使用提供方规定的验证与事件标识，将可信外部账号映射到本地租户；校验重复、乱序与状态转换。涉及计费时明确 provider 与本地权益各自的事实来源，不把浏览器返回成功当成已到账。不涉及计费的系统不强制添加支付模块。

## 前端也承担系统边界

从角色与业务任务设计导航、列表/详情、批量操作、表单、审计与设置之间的路径；复用设计系统的密度、组件状态与语义 token。可隐藏无权限入口改善体验，但服务端仍需拒绝非法调用。

大列表的分页/排序/筛选及批量选择语义与 API 一致。按实际数据量决定虚拟化；不能把十条假数据流畅当成大数据性能证据。区分后台任务“已受理”“处理中”“完成/部分失败”，提供进度和恢复入口，而非请求 202 后显示成功完成。

## 用纵向路径验证

选择能跨过真实边界的最小业务闭环：例如成员进入组织 → 创建资源 → 另一角色查看/拒绝修改 → 记录审计 → worker 处理副作用 → 刷新/重启仍可核对。每个结果应对应 UI、API、数据与任务状态，不能靠前端预置结果拼接。

根据采用的设计验证：

- 两租户与多个真实角色：伪造租户、猜测资源 ID、跨租户关联、列表/详情/搜索/统计/导出及后台执行的隔离。断言拒绝之外无写入、无事件和无数据泄露。
- 并发与恢复：版本冲突、重复操作、提交已成功但响应丢失、事务回滚、进程重启、worker 认领后崩溃、外部副作用失败。
- 组织切换：慢响应、旧缓存、未保存表单、成员撤销；核对实际前后端行为。
- 运行约束：迁移与数据兼容、必要索引、关联查询与分页；按用户需要设定和测量负载、延迟及成本，不把功能测试升级为容量证明。

记录部署方式、配置/密钥管理、schema 迁移、request/job ID 与 tenant 的关联、错误可观测性、恢复或回滚方式。只检查本次适用的运行风险，测试不得输出密钥或多租户敏感内容。

交付分别列出设计评审、功能、隔离/授权、恢复、UI 和性能证据。图纸完整不能证明实现可用；一条闭环通过也不能称整套大型 SaaS 已验证。采用 [验收与交付](delivery.md) 的状态区分。

处理器级 Request/Response 测试可验证模块集成与持久化，但尚未覆盖 HTTP 服务、浏览器 cookie 行为、反向代理或 UI 联调。分别标注，不把处理器测试命名为完整端到端验收。成熟身份/组织模块的限定实验与实际发现见 [复用集成验证](https://github.com/Jaxson-zip/agentic-craft-ui/blob/main/docs/REUSE_INTEGRATION_CASE.md)。
