# 多 Agent 协作

只有任务独立、宿主支持且当前授权允许委派时才并行。多 Agent 不是交付的必要条件；单人模式执行相同的契约与验收流程。

## 默认步骤

按顺序推进；后面各节是每一步的细则和常见误区。

1. 判断能否并行：任务独立、宿主支持、授权允许，三者都满足才委派，否则串行。
2. 先由单一负责人确定共享契约。
3. 给每个任务写简报：目标、验收条件、可写范围、只读依赖、基线版本、验证命令、产物返回方式。
4. 核对写入范围不交叉；锁文件、配置、共享类型和文档各指定唯一负责人。
5. 集成前审查每个任务的实际 diff 和证据，集成后重跑跨模块检查和主路径。

## 分工前

先明确共享接口与负责人。契约未定、同一文件需要多人改或存在顺序依赖时，先由单一负责人处理，再分派消费者工作。按能力与可用工具选 Agent，不根据模型品牌推定专长；不自动安装或调用额外付费 CLI。

每个任务提供：目标、验收条件、可写文件或目录、只读依赖、基线版本、其他改动的负责人、验证命令、产物返回方式。上下文只包含本任务需要的参考；快照须先检查是否仍适用。

例如，契约负责人先更新当前项目的接口定义；前端和后端分别消费已定契约。QA 可只读审查，也可在明确授权的测试范围写回归测试，不同时赋予“只能只读”和“可写 tests”的矛盾要求。

## 写入范围的实际含义

在共享工作目录中，Write Scope 是约定，不是操作系统权限。分派前核对范围交集；为锁文件、配置、共享类型和文档指定唯一负责人。通配符是否包含子目录需要明确。

宿主有独立 worktree、沙箱或文件权限工具时可使用其真实隔离能力，并说明实际启用了什么；独立 worktree 仍可能在集成时产生语义或文本冲突。没有这些工具时采用不交叉的任务或串行执行，不能宣称“零冲突”。

## 集成

主 Agent 检查每个任务的实际 diff、写入范围、契约和测试证据，再集成。改动超范围时先确认原因并处理，不能只凭子 Agent 的“已完成”声明验收。

共享接口变更由负责人协调并通知相关消费者；涉及外部聊天、邮件或服务的通信遵循已有授权。集成后重新跑受影响的跨模块检查和实际用户路径。

发生冲突时保留用户与其他 Agent 的改动，理解两侧语义后处理；有阻塞依赖就调整顺序，不反复开更多 Agent 掩盖问题。
