# 开工澄清与决策边界

用于新产品、重要选型、用户要求比较或已否定视觉的任务。小修复和已明确的方案按现有约束推进，不发一套固定问卷。

按主文件的当前决定记录，从请求、历史回答与仓库补齐目标用户/主任务、现有栈与品牌、硬约束和实际待定项。区分已确认、Agent 假设、用户尚未选择和已否定的方案；用户同意业务类型不等于认可技术栈、配色或动效。

## 什么值得问

| 决策缺口 | 问题应指向的结果 |
| --- | --- |
| 产品用途与范围 | 谁完成哪条核心路径？此次需要评审、预览还是实际实现？ |
| 新产品的复用边界 | 哪些能力直接用、哪些适配/二开、哪些属于产品差异？按能力解释取舍，不要求用户替整个项目做“独立或二开”的二选一 |
| 运行与使用约束 | 既有栈、自托管/托管、数据要求、内部/对外用途、必要预算边界；它们是否排除候选？ |
| 视觉方向确实待选 | 用户已有品牌/参考和已确认偏好是什么？需要看哪些有实质区别的片段才能选择？ |

只问当前依赖的缺口，问题少而有后果。用户不了解技术选型时，先提供可审阅的少量路线与取舍，再请求影响结果的决定，不把工程责任转成一长串技术选项。已有答案、仓库能查出的栈/组件、正常低影响实现细节不重复提问。

用户需求先于源码与模板：把必要结果、可接受的降级备选和 Agent 建议分开。没有明确要求就不预设开源、自托管或必须二开；不要围绕已找到的仓库功能重写需求。用户认可页面、接受一个备选操作或授权“继续”，不自动表示核心目标已变更。影响路线的能力未知时按 [生态调研](discovery.md) 先补证，无需让用户反复审批技术细节。

独立品牌与模块二开可以共存。根据用途、既有栈和实际适配性，由 Agent 逐项提出复用决定；只有许可、预算、部署或业务取舍确实需要用户选择时才问。不要把本应由工程判断解决的复用问题包装成产品路线审批。

## 答案未到时

可继续核对已有代码、候选资料、复用边界及比较标准；待定路线影响的依赖安装、底座锁定或大范围实现保持待定。没有回复不算选择；已有明确授权则按其继续，不额外制造审批。

用户要求两版视觉、不同动态节奏等时，保留这份具体要求。选择前的工作范围是比较用的关键页面/操作片段，不能把其中一版提前扩成整套产品。方向与数量没有要求时不强制“两版”。比较片段消费同一核心内容，展示排版/密度、语义配色和实际动态，避免只换主题色；具体方法见 [艺术方向与动效](art-direction-motion.md)。

## 可以宣称什么

需求澄清、资料评估、集成、行为验证、视觉选择与动态体验分别报告。对比度数值、控件正常态截图、架构图和行为测试不证明用户认可视觉；截图不能证明动画节奏。用户已否定的方向记录为未通过，不用新测试数量覆盖这条反馈。

选择某一方向只确认后续沿该方向推进，不能自动升级为字体、密度、控件、自适应和成品质量均已认可。用户说动效可以但界面仍普通时，保留动效认可，继续处理质感与布局；后续否定质量时更新当前状态，不能只引用先前的方向选择。

持续迭代可在现有文档用简短记录保留“维度、当前决定/问题、依据、下一步”。用户选择和技术检查采用不同状态：`selected / accepted / rejected / pending` 描述用户判断，`passed / failed / not-run` 描述限定检查。例如已选紧凑冷色工作区、动效可接受，但字体与间距被否定时，沿原方向修字体和布局；不重问风格，也不把修正后的截图自行标为用户已接受。新反馈只替代它影响的选择，保留其余有效答案。

复用决策先于通用底座自建，详见 [生态调研](discovery.md)。重复问卷、反复造示例、复制旧模板或不断增加文档，均不替代本次已授权结果。
