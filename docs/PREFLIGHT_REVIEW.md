# 开工与复用流程复审

查证日期：2026-10-13。当前交付是 agentic-craft-ui 修订与资料评估，不是协作产品开发。保留已确认偏好：面向产品/研发团队；未来先看两版有实质差异的视觉与交互、比较两种动态节奏。本轮不制作这些预览，也不重问这些选择。

## 已发生的失败

此前 Orbit 实验有 14 项行为测试与实现架构图，但它没有候选方案比较或复用决策记录。只询问业务类型后即选择原生 JS、手写会话/worker 和 SQLite；这些隔离实验的取舍没有证明适合用户需要的 SaaS 成品。用户否定了其产品质感，随后明确指出可能重复造轮子。

源文件核对：`saas-collab-lab/public/styles.css` 没有 transition、animation 或 reduced-motion 规则；界面采用深侧栏、浅卡片、蓝色操作与绿黄品牌字，包含较多实验说明与小号标签。该事实不能评价所有未来动画，却足以说明前次没有落实所需的动态体验。图纸、对比度和行为测试不能替代产品/视觉选择。

前次失败既有执行偏差，也有指导边界不足：

| 缺口 | 这次的改动 |
| --- | --- |
| 用户完善 skill，工作扩成新应用 | 入口先识别交付类型，示例仅检验明确假设 |
| “合理默认”覆盖了待定产品与视觉路线 | 明确已确认、假设、待选择与被否定；只问会改变结果的缺口 |
| 避免盲目加依赖被误读成全部手写 | 通用底座先看现有能力/成熟候选，再给适配或自建依据 |
| 整套产品、starter、单项库混为一谈 | 分层比较可复用能力、未覆盖部分、运行与升级成本 |
| 工程检查代替用户视觉认可 | 分开报告资料/集成/行为/视觉选择/实际动态状态 |

## 候选资料核对，不是已选技术栈

| 候选与层级 | 已核对的范围 | 适配判断与待查项 |
| --- | --- | --- |
| Plane：整套协作产品 | 主仓库介绍项目任务、cycles 与路线管理，展示 AGPL-3.0；当前默认分支 preview。官方自托管资料区分版本与许可。[仓库](https://github.com/makeplane/plane)、[许可证文件](https://github.com/makeplane/plane/blob/preview/LICENSE.txt)、[自托管资料](https://developers.plane.so/self-hosting/overview) | 适合作为整套产品定制路线的调查对象；不能把商业版本能力算入社区源码。还需确定产品用途、稳定版本、部署、定制和升级边界 |
| Huly / Platform Collective：产品/平台 | Huly 旧仓库声明冻结、托管服务停止，指向独立维护的 Platform Collective；两仓库展示 EPL-2.0，分支 develop。[旧仓库说明](https://github.com/hcengineering/platform)、[当前指向的仓库](https://github.com/Platform-Collective/platform) | 旧名气不足以支持直接采用；需追踪当前维护、发布和运维路线。没验证新仓库的发布/部署可用性，不作为默认底座 |

## 这次能作出的决定

先复用合适的现有能力；如果目标是定制现有协作产品，就评估整套产品边界；如果要独立品牌和业务，则比较 starter/模块组合。是否选择上述产品尚未确定，当前未选定新技术栈，也没有复制候选代码。

决定基础能力之前需核对内部使用/对外产品、既有栈、部署/数据约束、必要预算及许可/版本边界。这里列为未来产品工作的依赖，不在 skill 修订阶段要求用户立即做这些决定。

自建重点应落在真正的业务差异和产品表达。认证/组织、通用复杂控件或作业设施若适配成熟方案，使用其接口并验证实际集成；仍需自建时给出具体不适配点和维护成本。原实验保留作工程材料，不能默认延续为正式底座。

## 行为检查如何解释

同一 A/B/C 场景分别交给无 skill、冻结的修订前 skill、当前 skill，采用独立上下文，仅输出开工决策，禁止实现、联网或运行候选。场景覆盖新 SaaS 赶工、已有栈小修复/离线、视觉已被否定/只评审 skill。原始答复见 `docs/evaluation/preflight/`，场景见 [preflight.md](../tests/behavior/preflight.md)。

无 skill 与修订前条件已经提出了合理的复用路线、必要问题和证据边界，没有制造新的“失败基线”。实际修订依据是前述已发生的执行失误和用户反馈；离线答复不能证明后续真实使用必然遵守，不能据此计算能力提升或成功率。修订后具体审阅结果将在验收时记录。

修订后答复已审阅：A 在锁定底座前提出用途/路线/部署问题，分层比较能力，不将实验或默认视觉当成已选方案；B 保留现有栈与设施、离线推进，不额外提问或搜索；C 保持只评审 skill 的范围，并将用户否定的视觉与历史工程检查分开。三个条件都总体符合这些边界；结论是规则表达更明确，没有观察到可量化的新增能力。原始材料分别为 [无 skill](evaluation/preflight/no-skill.md)、[修订前](evaluation/preflight/old-skill.md)、[修订后](evaluation/preflight/revised-skill.md)。
