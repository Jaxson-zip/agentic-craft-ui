# Agentic Craft UI

把用户路径、视觉、运行时契约和交付证据连起来。按影响选择流程；用户意图、项目规则和现有授权优先。完善是把已授权的结果做实，不是增加流程、依赖或产品范围。

## 先定位任务

检查相关项目规则、当前改动、清单、锁文件及已有脚本，识别框架、样式、测试和运行方式。保留既有工具与其他人的改动，不自动安装 Biome、Zod、TypeScript、动画库或外部服务。

先确认这次交付是 skill 修订、方案评审、视觉比较、产品原型还是功能实现。用户评审 skill 时，示例只验证明确假设，不自动扩成完整应用。新产品、重要选型或视觉重做按 [开工澄清](references/intake.md) 核对已知与待定决策；沿用先前回答，不把未否定的默认方案当成用户已认可。

| 情况 | 推进方式 | 按需读取 |
| --- | --- | --- |
| 新产品、重要路线变化 | 从需求比较可直接采用的完整方案，先验证会否决路线的核心能力，再做必要的定制 | [生态调研](references/discovery.md)；定制 UI 时读 UI 参考 |
| 已定路线的较大交互变化 | UI-First：可点击主路径，明确模拟边界，再接真实契约 | [UI 与交互](references/ui.md) |
| 多租户 SaaS、跨领域业务系统 | 澄清产品与约束，评估现成底座及模块，再确定边界与纵向实现 | [生态调研](references/discovery.md) → [SaaS 架构](references/saas-architecture.md)；改 UI 时读 UI 参考 |
| 已有应用功能、重构 | Brownfield：沿当前实现定位，复用组件，渐进改变 | [架构与上下文](references/architecture-context.md)；改 UI 时读 UI 参考 |
| 纯后端、CLI、算法 | Logic-First：输入输出、错误与核心规则先行 | [验收与交付](references/delivery.md) |
| 小修复、文案调整 | 直接定位与验证，跳过完整原型和架构流程 | 仅有相关风险时读取参考 |

只读相关参考。新产品选型、明确要求寻找模板或复用可能节省大量工作时，读 [生态调研](references/discovery.md)。小功能、已有栈与离线任务不以全网搜索作为开工前提。

**新产品的开工关口。** 在搭底座或扩建定制 UI 前，按 [生态调研](references/discovery.md) 留下简短、可核对的决定：用户的核心结果与硬约束、可直接使用的成品/服务及现有能力、最可能否决路线的能力验证、仍需自建的具体缺口。按需求找方案；GitHub 只是来源之一，未要求开源/自托管时也比较现成服务。候选有什么功能不能反推用户需要什么。采用几个库或成熟数据库不等于已排除完整方案。

决定方案能否成立的能力先做最小验证；无法实测时保留未知，暂缓依赖该假设的扩建，可继续资料核对或用户已授权的独立片段。不要用保存、同步、build 或页面好看来抵消核心能力未证实。已定平台的小改动、纯视觉比较和明确的学习实现不重走全市场选型；既有授权无需新增审批。

避免盲目安装不等于零依赖、全部手写；认证/组织、通用复杂控件或任务运行设施的自建需要具体的不适配依据。“只是测试”不是自建豁免：明确要验证的假设，优先使用现成实现；只有隔离该假设确有必要或用户明确要求学习实现时才做限定替代，不把实验底座自动升级为真实产品路线。

用户要求鲜明风格、耳目一新、品牌表现或有叙事的动效时，读 [艺术方向与动效](references/art-direction-motion.md)。从产品概念推导构图、字体、素材和标志性交互；视觉预设只是基础 tokens，不能替代艺术方向。已有界面仅修排版时仍按原方向精修。

## 关键决策与实现

1. **明确成功条件。** 提取核心用户路径、可观察结果、范围和约束。未知的产品路线、用途/部署、复用与品牌方向会改变方案时先问；仅暂停依赖这些答案的选型和实现，继续资料核对。小修复、已定方向与低影响细节可合理默认。
2. **做出可审阅的视觉决定。** 继承现有设计系统与用户已选方向；方向未定时可提出明确假设与具体预览。用户要求比较方案或已否定当前方向时，先做被授权的比较片段，等待其选择再扩展成品；不能反复微调被否定的默认样式。普通任务不固定要求风格审批。浅深、密度与布局按场景选择；可选 [视觉预设](references/visual-presets.md) 只提供基础 tokens。
3. **保持契约一致。** 确认字段、枚举、单位、错误、身份和状态变化。沿用已有类型和运行时校验；视觉调整也要核对表单选项与 API，不能私增业务枚举或让文案承诺尚未发生的操作。
4. **读到影响边界。** 用检索、语言服务或索引定位，再读实现、消费者、测试及配置。索引是入口，不是完整事实；不限制固定文件数量。源码改变后核对相关快照。
5. **修复以失败证据为起点。** 先复现，再做最小有效改动并回归。无法稳定复现时用日志或隔离实验说明不确定性，不用行数上限阻碍调查。
6. **落实反馈与失败恢复。** 覆盖适用的 loading、empty、error、success；保存成功由实际结果确认。保留失败输入，处理项目实际的冲突与重试语义；超时可能已提交时不能盲目重发写请求。
7. **用真实证据收尾。** 按 [验收与交付](references/delivery.md) 选择检查；UI 检查见 UI 参考。分别记录 passed、failed、blocked、not-run、not-applicable。HTTP 200、mock 或 build 通过不能替代业务验收；无横向溢出不等于自适应可用，选择视觉方向不等于成品质感已通过。

持续打磨时，沿用已确认选择，先定位当前失败的维度和代表路径。视觉、动效、自适应、功能与复用分别更新状态；修复当前缺口后复查相邻场景，不能用另一个更容易通过的示例替代。状态记在现有决策或验收文档，不为普通小改动增加仪式。

用户已授权“反馈 → 修改 → 验证 → 验收”时，由当前宿主会话执行实际工作，并用已有工具将结果关联到原任务；自动建任务或填进度不能替代修改和验证。技术通过记为待验收，用户明确接受后才关闭。已有授权无需重复询问；skill 本身不会启动后台执行器。接入记录与执行边界见 [验收与交付](references/delivery.md)。

## 架构与协作

涉及模块边界、API、模型或权限时，读 [架构与上下文](references/architecture-context.md)，更新受影响的文档；图表服务实际问题，无持久化任务不画 ER 图。

复杂 SaaS 不能用控件样例或单用户 CRUD 证明系统能力。按 [SaaS 架构](references/saas-architecture.md) 维护可追溯的边界图、关键流程和数据模型，验证适用的租户隔离、授权、并发与后台任务；已有系统的小改动只更新受影响部分。

任务可独立并行、宿主允许且具备工具时，读 [多 Agent 协作](references/collaboration.md)。小改动、有顺序依赖或用户要求单人时串行；写入范围是协作约定，只有实际权限机制才称强制隔离。

## 资源与工具

- [scripts/repo_map.py](scripts/repo_map.py)：Python 标准库的 JS/TS/Vue 轻量符号索引，含行号、指纹和快照检查。先看 `--help`；从已知 skill 路径运行，目标为应用根目录。它不是 AST、调用图或死代码检测。其他语言或工具缺失时用 `rg`、语言服务及源码，不虚构执行结果。
- [assets/themes.css](assets/themes.css)：可选浅色/深色语义色与少量组件样式。按项目适配，不覆盖现有品牌；复制前读视觉预设的适用范围。
- [assets/theme-preview.html](assets/theme-preview.html)：无需安装依赖的配色预览，可本地打开；展示颜色及按钮状态，不代表完整产品设计或无障碍认证。

## 交付

说明实际结果、改动与验证结果、具体未验证项，附可审阅文件或原型。继续完成已授权范围；外部发布按现有授权与宿主规则执行，skill 不增加权限。
