# 开工决策答复

以下仅为依据给定事实提出的动作与交付口径；没有运行候选产品、实现功能或验证浏览器效果。

## A：新 SaaS，赶工与未知复用路线

### 下一步动作（按依赖排序）

1. 固定已知要求：服务产品/研发团队，覆盖项目、迭代、任务；先看两版明显不同的视觉与交互预览，同时比较两种动效节奏。这两项已决定，不再询问。十五分钟的目标定为可供同事讨论的下一步决策材料。
2. 根据已提供的候选事实整理路线比较，分别列出可复用能力、缺失能力与核实事项：Plane 可作为完整协作产品二开的候选，社区/商业边界仍需核实；Next.js SaaS Starter 可作为自有产品的登录、团队、计费和后台底座，项目协作业务仍需实现；Better Auth 的组织插件可承担组织、成员、邀请与访问控制，但业务数据隔离仍需单独设计。UI 组件和动画库只能提供界面基础，不能替代业务或艺术方向。
3. 保留现有实验，梳理其项目/迭代/任务行为、数据结构与可迁移部分；将原生 JS UI、手写本地身份、worker 和 SQLite 标为现有实验方案，不能仅凭行为测试通过就定为新产品架构。
4. 在路线问题确认前，拟定两版预览的内容与比较标准：同一核心任务流程，分别采用显著不同的配色、字体层级、布局和交互表达；每版展示两种动效节奏，并规划减少动态效果的替代方式。当前只提交预览计划，不创建应用或演示。
5. 获得路线和关键约束后，再核对候选实际适配性，确定身份、业务隔离、部署和许可边界，随后实施两版预览并收集选择。视觉确认后再扩大实现。

### 必要问题

- 优先选择完整协作产品二开，还是建立自有品牌的新产品？若尚不能决定，本次交付保留两条路线及各自下一步核实项。
- 是否有必须沿用的技术栈、部署环境或数据驻留要求？没有硬约束时可先比较路线，技术栈选择随路线收敛。
- 产品计划为内部使用、商业闭源 SaaS，还是开源产品？是否接受候选产品的社区/商业能力边界与许可约束？具体适用性需在选型后核实，不能从候选名称推断。

这些问题影响实际选型和实现，不阻碍十五分钟内形成比较材料；不重问目标用户、两版预览或两种动效节奏。

### 可继续的独立工作

拟整理候选比较表、现有实验复用清单、两版视觉与交互预览说明、动效比较维度及后续验证清单。现有 14 项行为测试通过可作为题目给定的实验状态记录，不能称为本次重新验证。

### 暂不做的事

不因截止时间直接确定架构，不重写身份系统，不安装或运行候选，不迁移实验、不增加完整业务、不发布产品，也不将库选型等同于设计完成。

### 可交付状态

十五分钟内拟交付“下一步决策材料”：路线比较、待确认约束、实验复用边界与两版预览计划。该材料完成不等于候选验证、预览实现、视觉认可或 SaaS 产品完成。本次答复只是决策建议。

## B：已有应用，小范围功能且离线

### 下一步动作（按依赖排序）

1. 以现有 Vue 3、FastAPI、PostgreSQL、OIDC、设计系统、共享表格和权限中间件为固定边界，确认现有批量入口、单任务服务、选择状态及版本冲突/审计事务的衔接位置。此处为拟检查项，当前没有读取工程。
2. 拟在 `POST /tasks/batch-archive` 内复用单任务服务和现有权限检查，对批量目标逐项适用既定归档与冲突规则；保持既定业务层事务和审计边界，防止部分失败时出现未经定义的数据状态。
3. 拟在现有列表选择状态上增加批量归档动作，沿用设计系统处理进行中状态、防止重复提交及成功/失败反馈，并按既定语义更新列表和选择状态。
4. 拟先执行离线可用的服务与接口验证，再验证前端选择、提交和反馈行为。最后记录实际执行的检查、结果与无法覆盖的部分；三十分钟内优先完成这个最小功能范围。

### 必要问题

当前没有需要重问的业务或选型问题。用户、角色和归档语义已经明确，离线、不装包、不换架构也已确定。若检查时发现代码与既定语义冲突或出现无法从已有约定判定的事务行为，才提出该具体阻塞问题。

### 可继续的独立工作

拟检查并复用已有入口、单任务服务、权限中间件、审计事务和选择状态；使用本地已有依赖完成最小修改与可执行验证。更改归档字段不需要调整 OIDC。

### 暂不做的事

不联网、不装包、不替换技术栈，不引入新的身份、表格或权限方案，不重做设计系统，不开展与批量归档无关的产品选型。

### 可交付状态与验证边界

拟交付批量归档的最小代码变更与验证记录。检查重点包括正常批量归档、空选择、无权访问目标、版本冲突、混合成功/失败或事务回滚、审计一致性以及重复提交，预期行为均遵循已明确的语义。

离线可执行的真实结果才能作为证据。如果本地数据库、测试工具或浏览器不可用，应标明相应验证未执行；接口测试通过也不能代替浏览器交互验证。仅在实现和必要检查实际完成后，才能声明相应范围完成；当前只能提交拟执行方案。

## C：视觉已被否定，工程证据不能代替设计选择

### 下一步动作（按依赖排序）

1. 依据提供的历史事实审查开工流程缺口：只确认业务类型，未记录候选方案比较与复用边界，未取得视觉方向认可。当前没有读取 skill 正文，因此这只是对给定流程记录的审查，不能声称完成了 skill 全文审计。
2. 补齐拟议流程中的候选比较和复用边界，沿用 A 的路线问题与已确认偏好，区分产品底座、身份/组织能力、业务能力、UI 基础和艺术方向各自承担什么。
3. 将工程状态与设计状态分别记录：四种架构图、14 项行为测试通过及 320px 越界修复是给定工程事实；它们不能证明配色、排版、品牌辨识度或动效符合用户要求。
4. 指出设计决策的缺失：现有深侧栏、浅卡片、蓝色按钮和绿黄品牌字已遭否定；CSS 没有 transition、animation 或 reduced-motion 规则，因而不能宣称已提供两种动效节奏。拟将两版明显不同的视觉与交互预览、两种节奏及用户选择设为后续设计确认环节，本轮不继续制作演示。

### 必要问题

沿用 A 中尚未确定的产品路线、技术栈/部署硬约束及商业/开源模式问题，不重问目标用户或预览偏好。本轮流程审查可先完成；实际底座选型需要这些约束，视觉和动效选择需要用户看过预览后的反馈。

### 可继续的独立工作

拟交付流程缺口清单、候选能力与复用边界表、设计确认环节及交付状态说明。原有业务行为、数据与服务中的独立逻辑、已有验证和响应式修复可作为后续复用候选；迁移后仍需按新边界验证。架构图可帮助说明现状，不能直接作为新路线的决定。

### 暂不做的事与必须等待的决定

不继续造演示、不修改 skill 或应用，不把现有侧栏/卡片布局当作已获认可的设计基础。完整产品二开还是自有产品、最终技术栈与部署、许可和商业边界需要相应约束与核实；最终配色、排版、交互方向和动效节奏需要两版预览及用户反馈。

### 可交付状态

本轮拟交付“基于给定事实的开工/复用流程审查建议”。现有工程具有给定的行为与响应式验证记录，视觉方向尚未获认可，动效偏好尚未通过预览落实。不能宣称视觉或产品已完成，也不能将流程建议写成已修改并验证的 skill。
