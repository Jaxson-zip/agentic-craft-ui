## 修订前失败证据

用户要在 iOS 上尽量自动记录微信/支付宝消费并在电脑查看，明确要求优先复用。实际执行先接入 Firefly，再修改 Pico 手机界面；保存、读回、构建等局部检查完成后，手机自动采集仍未完成。用户提示现成免费工具后，才进一步验证完整产品候选。这个顺序导致部分定制投入可能返工。

本地工作记录与 `G:/skill/personal-ledger/beecount-evaluation/EVALUATION.md` 可核对：旧版有账本与移动端读取，采集未完成；蜜蜂已有原生 AppIntent 路径与中文 Web，限定云端对照通过，但真机采集仍未验证，且当前核对的截图源码依赖视觉模型配置。不能把这一事实变成“蜜蜂已全面解决问题”。外部项目证据不随 skill 打包，复验所需的去标识场景另存于仓库测试文件。

这是实际失败案例，不是无 skill 对照实验。此前执行责任属于 Agent；已有指令的存在不能证明执行有效，也不能证明只修改文档即可解决问题。

2026-10-22 安装修正：冻结主文件改名为 `before/SKILL.snapshot.md`，正文与 SHA-256 不变，清单只更新文件名。避免完整安装或克隆本仓库后，历史 `SKILL.md` 被发现为第二个同名技能；历史评估结论不变。

## 根因与待验证的改动

1. 主入口给新产品直接指定 UI-First，复用规则与它并存但未明确先后。需先判断整体路线及关键可行性，再决定是否需要自定义原型。
2. 调研偏向可二开的源码和底座，未把可直接使用的成品/托管服务作为同等入口。需求应独立于候选功能，开源只是约束之一。
3. 自动采集等决定方案成立的能力被延后；保存/同步等局部证据持续累积。需先验证最可能否决路线的能力，并保持核心验收与局部检查独立。
4. 受阻时继续扩建依赖该假设的界面。需限定为独立工作或能回答具体疑问的实验，不新增审批或阻断无关小修复。

## 本轮实际修订

- 主入口拆开“新产品路线”与“既定路线交互”，先做复用/核心验证，再进入所需的 UI-First；UI 参考和 README 同步。
- 调研纳入可直接采用的服务，先确定用户结果与硬约束，再找候选；不默认开源、自托管，也不从仓库功能反推需求。
- 以一份简短能力/证据/缺口/下一动作表限定二开；核心未知时只暂停依赖它的扩建，已授权独立工作可继续。
- 澄清与交付分别保留原始目标、降级备选、局部认可；核心未过时整体需求仍未满足。
