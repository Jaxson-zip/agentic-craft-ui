# SaaS 架构行为评估场景

这是待执行的冷启动评估，不是已运行基准。当前独立 SaaS 切片的实际记录见 [架构案例](../../docs/SAAS_ARCHITECTURE_CASE.md)。

## 给评估 Agent 的用户请求

使用 agentic-craft-ui 完成已有多租户项目协作平台的任务归档功能。沿用现有栈；owner/editor 可归档，viewer 不可写。任务变更、审计和通知事件需可靠关联。补充受影响的架构图，并展示真实 UI 与失败恢复证据。不要重建整个系统或更换设计系统。

原始事实应随隔离测试仓库提供，而不是只作为文字：两个租户、三种角色；前端组织切换与请求缓存；API 的组织路由与成员中间件；SQL 中任务/项目复合键、审计、outbox；一个 worker；现有版本字段。仓库保留真实脚本与锁文件。准备正常、越权与旧版本的可复现记录，保留一条模拟发送失败的事件。评估者不事先获得下面的审阅标准。

## 审阅实际产物

核对代码、图与运行证据，不以生成的计划或功能数量评分：

- 是否读到 route → 授权 → 领域 → SQL/事务 → worker，以及 UI 消费路径，而不是把 repo_map 当调用图？
- 是否沿用真实 tenant 来源与角色约束，检查跨租户详情、关联和作业，而非仅前端隐藏入口？
- 是否明确 archive 语义、版本冲突、响应丢失和重试范围，保留真正未验证项？
- 架构/数据/关键流程图是否标明现状与变更、附源码依据，并在实现后同步？
- UI 的组织切换、旧响应/缓存、失败恢复是否与 API 结果一致？
- 是否展示至少一条真实纵向路径，以及拒绝、回滚或任务失败的无副作用断言？
- 是否避免凭“大型 SaaS”强加微服务或额外云服务，也不把小型切片结果升级为生产容量证明？

未来对照应给各条件同一隔离仓库、任务与资源预算，保留真实产物、执行结果和限制。当前没有执行该对照，不能据此声称 skill 普遍提升模型能力。
